### E2E cold-boot 註記（沿用 M4，重要）

`npm run test:e2e:local` 跑完整套件時，M5 heavy 頁面首次編譯會超過 Playwright per-action timeout，造成**假 fail**。對已暖機的持久 dev server 單獨重跑穩過。可靠跑法：

```bash
# 先起持久 server 並暖機 M5 頁面
node scripts/with-local-supabase.mjs npm run dev -- --hostname 127.0.0.1 --port 3100 &
curl -s -o /dev/null http://127.0.0.1:3100/app/schedule   # warm
# 再對 warm server 跑
PLAYWRIGHT_BASE_URL=http://127.0.0.1:3100 \
  node scripts/with-local-supabase.mjs npx playwright test tests/e2e/m5-*.spec.ts
```

**接手方看到 M5 E2E red 先確認是否 warm server，別誤判為 code 缺陷。** 待辦：給 M5 E2E 第一個互動加 readiness gate / CI 預暖。

## M5 做了什麼

- **DB（202607190004）**：16 個工單操作 RPC — create、schedule（原子排程+指派+轉移）、check_schedule_conflicts、list（keyset，**技師只看自己**）、detail（角色裁欄，技師無成本）、assignment 生命週期、checklist create/respond/complete、photo verify-and-mark-ready（覆核 MIME magic bytes+sha256+尺寸才標 ready）+ signed read + soft-delete、**force_complete（僅 owner/admin，reason 必填，獨立 `force_completed` event，絕不設 customer_signed_at）**。
- **DB（202607190006）完工 gate 硬化**：必填 photo 型 checklist 項改由 **ready 證據**滿足（不依賴 client 的 best-effort respond 寫入），死鎖修在權威層。
- **狀態機**：接線 `work-order-state.ts` domain（單一真相），SQL/route 都不重刻矩陣。依 domain-glossary §4 **不擴充 status enum**（已確認/待確認/未到場/需再訪為 UI 投影）。
- **API**：work-orders CRUD+actions、assignments、schedule + conflict-check、checklists、photos；mutation 回應帶 `notification:{status:"not_sent",reason:"line_delivery_deferred_to_m6"}`（誠實標示 LINE 未接）。
- **UI**：dispatcher 排程板 + 指派 sheet + 工單詳情；技師任務列表（只看自己）+ 現場執行頁（狀態動作、checklist 含 photo/choice 輸入、前後照/異常擷取、被擋完工具名缺項、force-complete sheet 標示「例外完工，非客戶簽認」）。

## 怎麼在本機測 M5（給使用者）

dev server 在 `http://127.0.0.1:3100`（本機 Supabase + Mailpit 55324）。接續 M2–M4 流程：報修→分流→報價→客戶接受→**轉工單**後：

1. **dispatcher**：`/app/schedule` 看未排程工單 → 排程時段 + 指派技師（衝突會提示）。
2. **技師**：`/app/my-work-orders`（只看自己）或 `/app/today` → 開工單 → 出發/到場 → 拍前後照 + 填 checklist → 完工。缺必要照片/checklist 會被擋並**具名缺項**。
3. **owner 例外完工**：缺項時 owner 可填理由強制完工（明確標示非客戶簽認）。

（測試技師端需先有第二個 membership；可在 Supabase Studio 55323 手動加，或用 seed 的測試租戶。）
