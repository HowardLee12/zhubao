## M7 做了什麼

- **AI extractor seam**（`src/server/integrations/ai/`）：`AiExtractor` 介面 + `FakeAiExtractor`（ok/unavailable/timeout/bad_output）+ `FireworksAiExtractor` **deferred stub**；`createAiExtractor()` 依 `FIREWORKS_AI_LIVE` 切換。
- **對話聚合**（Wave 1 DB）：LINE 訊息聚合成一段對話（一 sender 一 open conversation）、extraction worker 產生草稿。
- **降級 gate（DB 保證）**：`intake/gateway.ts` 的 try/catch 把任何 AI 失敗降級成 `mark_extraction_failed`（origin=manual 草稿），永不 throw 出邊界、訊息不遺失。E2E 已驗證。
- **草稿 review UI**：`intake-draft-review.tsx` — 不可變原始訊息 + AI 欄位含每欄信心/來源 + 缺欄 + 確認建 service_request（重用 M3 convert）。inbox「待確認 · LINE」badge。
- **confirm resolve-or-create identity**（review 修的 HIGH）：陌生 LINE sender（無綁定身分）確認草稿時，`confirm_intake_draft` 從對話的 `(org, channel, line_user_id)` 建立客戶 + LINE 身分並綁定對話——**第一次來訊的陌生客戶也能轉進件**（原本會 500）。

## 真實接線（M7 完成後仍留的 deferred seams）

在使用者提供憑證前全用 fake 跑通。要接真實時：
- **真實 Fireworks**：填 `FireworksAiExtractor.extractIntake` body（POST `api.fireworks.ai` chat/completions，`FIREWORKS_API_KEY` server-only，用 `extractionResultSchema.parse` 驗——壞輸出必須 throw 以觸發降級）、設 `FIREWORKS_AI_LIVE=1`。`.env.example` 有佔位。
- **真實 LINE 圖片下載**：填 `RealLineContentFetcher` body（`api-data.line.me` 固定 endpoint，SSRF-safe）、設 `LINE_CHANNEL_LIVE`。
- **真實 LINE channel / push**：M6 既有 deferred（`RealLineMessenger` + `LINE_CHANNEL_*`）。
- **注意**：webhook message 事件 → `ingest_inbound_message` 的接線（`ingestMessage` seam）目前建好但尚未接進 webhook-process 的實際 HTTP 路徑；接真實 LINE 時要把它 wire 起來（seam 已就緒）。

- **測試隔離**：`test:sql` 的 pgTAP `disable_line_channel` 測試會 commit 停用狀態污染共享 DB，導致緊接著跑的 `test:integration`（M6 notification dispatch）claim 不到通知而失敗。**跑 integration 前先 `db reset`**（或分開跑，CI 本來就分 job）。這不是 code bug，是跨套件污染。
