# Renoly v2 產品規格

文件狀態：Draft v1  
目標版本：MVP / Private Beta  
主要語言與市場：繁體中文、台灣，首波北北基桃  
相關文件：[前端規格](./frontend-spec.md)、[使用者旅程與驗收條件](./user-journeys.md)

## 1. 產品摘要

Renoly 是給 2–10 人小型工程與到府服務團隊使用的 LINE-first 接案到收款工作台。店家不用要求客戶安裝 App；客戶從原本使用的 LINE 進入報修／詢價表單、查看報價、確認時段、簽認完工與收到保養提醒。老闆、派工人員與技師則使用手機優先的 Web App / PWA 管理整個流程。

產品要解決的核心問題不是單純的「派工」，而是把散落在 LINE 聊天、電話、紙本、相簿與個人記憶中的工程資訊，轉成可追蹤、可交接、可稽核、可回訪的營運流程。

產品承諾：

> 把 LINE 裡的工程詢問，變成不漏掉的報價、工單、施工紀錄與收款。

## 2. 定位與市場邊界

### 2.1 理想客戶輪廓

首要客戶是符合下列條件的業者：

- 團隊規模 2–10 人，包含老闆、行政／派工與現場技師。
- 主要從 LINE、電話、Facebook、Google 商家或轉介紹接到詢問。
- 每月約有 20 張以上詢價／工單，或同時進行 3 個以上小型工程。
- 報價前需要客戶照片、地址、設備資訊或現場勘查。
- 現場工作需要照片、檢查紀錄、追加項目、簽認或完工證明。
- 完工後仍有請款、保固、保養或再次服務機會。
- 現況依賴 LINE 聊天紀錄、行事曆、試算表、紙本或老闆記憶。

首波垂直產業：

1. 冷氣清洗、安裝與維修。
2. 水電維修與小型水電工程。
3. 抓漏、防水與相關修繕。

後續可擴張產業包括家電維修、清潔保養、油漆、泥作、木工、鋁窗、鐵工、玻璃、系統櫃、廚具與局部裝修。

### 2.2 不適合的客戶

MVP 不以以下客群為主要目標：

- 單人且每月工單極少、沒有交接或追蹤需求的接案者。
- 大型營造、完整室內設計公司或需要工地 ERP 的企業。
- 需要即時庫存、採購、薪資、會計總帳、估驗計價或複雜簽核的組織。
- 需要大量路線最佳化、車隊管理或 call center 的服務公司。
- 期待平台提供消費者流量或媒合訂單的業者。

### 2.3 產品不是什麼

Renoly v2 不是：

- 消費者媒合市集。
- 通用 CRM 或完整 ERP。
- 全自動 AI 維修診斷工具。
- 完整 POS、庫存或電子發票系統。
- 原生 iOS / Android App。
- 取代店家自己的 LINE 官方帳號。

## 3. 產品原則

### 3.1 LINE 是客戶入口，Web App 是團隊工作台

客戶不需要註冊 Renoly 帳號，也不需要下載 App。店家可從自己的 LINE 官方帳號圖文選單、聊天訊息或 QR code 導向品牌化表單與安全分享頁。店內成員使用 PWA 處理需要持續操作、權限控管與資料管理的工作。

### 3.2 一個共通核心，多個產業模板

所有產業共用客戶、地點、案件、報價、工單、照片、通知、收款與活動歷程。產業差異以模板、欄位設定、檢查表與選配模組呈現，不建立彼此割裂的產品或資料庫。

### 3.3 人工確認優先

系統可以整理文字、照片或語音成草稿，但涉及報價、診斷、派工、對客通知、追加款與完工結果時，必須由有權限的人員確認。MVP 不讓 AI 自動判斷故障或自行承諾價格。

### 3.4 每次交接都有上下文

任何人打開案件，都應在 30 秒內理解客戶是誰、地點在哪裡、目前狀態、下一步、承諾時間、最新報價、負責人、現場紀錄與待收款。

### 3.5 現場操作要比傳 LINE 更省力

技師端必須能單手操作、弱網路可用、拍照後自動分類、少打字、狀態明確。若紀錄工單比直接傳 LINE 更慢，產品即不成立。

### 3.6 可稽核但不過度承諾法律效力

報價確認、追加確認與完工簽認保留版本、時間、對象、來源與事件紀錄。產品對外稱為「可稽核簽認紀錄」，不宣稱一般 LINE 點擊等同特定法律形式的電子簽章。

## 4. 共通核心流程

完整價值鏈如下：

詢問／報修 → 分流與補資料 → 報價／現勘 → 客戶確認 → 排程與派工 → 現場執行 → 異常／追加 → 完工簽認 → 請款／收款 → 保固／保養／再次服務

MVP 的共通核心包括：

1. 將 LINE 或人工收到的需求建立成案件。
2. 集中客戶、服務地址、聯絡方式、照片與對話摘要。
3. 建立報價草稿、版本與客戶版分享頁。
4. 建立一次或多次工單並指派技師與時段。
5. 由技師記錄出發、到場、檢查、施工前後照與完工。
6. 記錄追加／追減、客戶確認與工單活動歷程。
7. 追蹤待請款、部分收款、已收款與逾期。
8. 留存設備／服務履歷、保固期限與回訪日期。
9. 透過 LINE 傳送經人工確認的通知與安全連結。
10. 讓老闆以少量 KPI 看見漏單與營運瓶頸。

## 5. 兩種產業模板

店家導入時選擇主要模板。模板只決定預設用語、欄位、狀態、檢查表與功能顯示；共通資料仍使用相同核心模型。owner 可在設定中調整模板，個別案件也可切換案件類型。

### 5.1 到府服務模板

適用產業：冷氣、家電、水電維修、清潔與定期保養。

預設特性：

- 案件通常由一次詢問開始。
- 一個案件可有一至數次到場工單。
- 重視可預約時段、設備資訊、快速報價與到場狀態。
- 現場紀錄以檢查表、前後照片、耗材／服務項目為主。
- 完工後有保固或 6／12 個月保養回訪。

預設案件階段：

待處理 → 待補資料 → 待報價／待現勘 → 待客戶確認 → 待排程 → 已排程 → 進行中 → 待收款 → 已完成

### 5.2 小型工程模板

適用產業：抓漏、防水、油漆、木工、泥作、鐵工、系統櫃、局部裝修。

預設特性：

- 常需要現勘與多版本報價。
- 一個案件可包含多日、多工種或多階段工單。
- 重視施工範圍、排程、前中後照片、追加／追減與階段請款。
- 完工後重視保固範圍與可稽核簽認紀錄。

預設案件階段：

新詢問 → 待現勘 → 報價中 → 待客戶確認 → 待開工 → 施工中 → 待驗收 → 待收款 → 保固中／已結案

### 5.3 首波產業預設

| 產業 | 主要模板 | 預設專屬欄位／檢查表 | 主要回訪 |
|---|---|---|---|
| 冷氣 | 到府服務 | 品牌、機型、設備類型、台數、錯誤碼、冷房狀況、前後照 | 清洗／保養 6 或 12 個月 |
| 水電 | 到府服務，可轉小型工程 | 問題類型、漏水／跳電位置、是否可斷水斷電、材料與測試結果 | 保固到期、定期巡檢 |
| 抓漏／防水 | 小型工程 | 漏水位置、天候、含水／測試紀錄、施工範圍、分階段照片 | 雨後回訪、保固檢查 |

## 6. 使用者與權限

### 6.1 店內角色

MVP 可由店家指派的角色固定為 `owner`、`dispatcher`、`technician`。後端資料模型預留 `admin`、`accountant`、`viewer`，但 Phase 1 不在導入流程或成員介面開放，避免小團隊一開始就承擔不必要的權限複雜度；其跨層定義見[領域詞彙與跨層映射](./domain-glossary.md)。

#### owner（老闆／管理者）

- 管理組織、方案、成員、角色、LINE 串接與模板。
- 查看所有客戶、案件、報價、工單、收款與營運指標。
- 核准並送出報價、追加、重要通知與退款／作廢操作。
- 管理服務價目、檢查表、通知模板與自動回訪規則。

#### dispatcher（行政／派工）

- 建立與編輯客戶、案件、報價草稿、工單與排程。
- 指派技師、處理改期、發送已授權的通知模板。
- 查看組織內案件、客戶與一般收款狀態。
- 預設不可管理方案、密鑰、成員角色或永久刪除資料。
- 報價送出與追加確認是否需 owner 核准，由組織政策決定；MVP 預設需核准。

#### technician（技師）

- 查看被指派的工單與完成工作所需的客戶／地址資訊。
- 更新出發、到場、施工中、待確認、完工等工單狀態。
- 上傳照片、填寫檢查表、記錄材料／異常與提出追加草稿。
- 預設不能查看成本、毛利、全店客戶名單、其他技師工單或收款總覽。
- 工單結束後僅能查看與保固／補件相關的必要資料。

### 6.2 客戶

客戶不是組織成員，不建立後台帳號。客戶透過 LINE 或簡訊收到一次性／限時安全連結，可完成：

- 填寫需求、上傳照片與選擇可約時段。
- 查看客戶版報價與版本摘要。
- 接受、拒絕或要求聯絡。
- 確認預約、改期需求、追加項目與完工結果。
- 查看付款資訊、保固摘要與服務紀錄。

高風險或含個資的頁面應要求二次驗證，例如手機末三碼或 LINE 身分綁定；連結可撤銷並有到期時間。

## 7. 核心領域物件與定義

### 7.1 組織

organization 代表一間付費店家，是所有營運資料與權限隔離的邊界。每筆客戶、案件、工單、報價、照片與通知都必須屬於且只能屬於一個 organization。

### 7.2 客戶、地點與設備

- customer：個人或公司客戶，可有多個聯絡人。
- location：實際服務地址，包含樓層、停車、門禁與現場注意事項。
- asset：選配的設備／標的，例如一台冷氣、熱水器或抽水馬達。沒有設備概念的工程可不建立。

### 7.3 案件

case 是從詢問到收款／結案的商業容器。它保存來源、服務類型、優先度、負責人、目前階段、下一步與所有關聯資料。UI 對外統一稱「案件」，避免同時出現 lead、request、project 等內部術語。

案件類型：

- service：一次或少數幾次到府服務。
- project：多日、多階段小型工程。

### 7.4 報價與版本

quote 代表同一輪報價；quote version 是不可覆寫的版本快照。草稿可編輯，送出後不得原地修改；變更必須建立新版本。客戶頁只傳送售價與公開說明，成本、毛利與內部備註不得進入客戶回應或前端 render tree。

報價狀態：

草稿 → 待核准 → 已送出 → 已接受／已拒絕／已失效／已撤回

### 7.5 工單

work order 代表一次可被排程、指派與完成的現場任務。單次清洗可只有一張工單；多日防水工程可有現勘、施工、試水與驗收等多張工單。

工單狀態：

未排程 → 已排程 → 已確認 → 已出發 → 已到場 → 施工中 → 待客戶／內部確認 → 已完工

例外終態：

已取消、未到場、需再訪

狀態跳轉必須記錄操作者、時間與原因。取消、完工回退、跳過現場步驟等例外操作需填理由。

### 7.6 現場紀錄

現場紀錄包含：

- 工單事件時間軸。
- 檢查表與量測值。
- 施工前、施工中、施工後、異常、材料與文件照片。
- 文字或語音轉文字備註。
- 客戶不可見的內部備註。
- 客戶可見的完工摘要。

### 7.7 追加／追減

change order 屬於案件，並可關聯提出它的工單。任何金額變更都需明確列項、原因、稅額／總額、版本與客戶確認狀態。未確認的追加不可自動併入已確認報價或收款金額。

狀態：

草稿 → 待內部核准 → 待客戶確認 → 已接受／已拒絕／已撤回

### 7.8 收款

payment request 代表一筆應收，可由報價訂金、階段款、追加款或尾款產生。MVP 記錄應收、到期日、付款方式、部分收款與人工標記；線上金流可作為後續整合。

狀態：

未開立 → 待付款 → 部分付款 → 已付款

例外狀態：

已逾期、已作廢

### 7.9 保固、保養與回訪

- warranty：定義起訖日、範圍、排除項目與關聯案件／設備。
- maintenance plan：定義下次服務日期、週期、通知提前日與是否需人工核准。
- follow-up：實際待辦／通知紀錄，可轉為新案件並保留來源關聯。

## 8. MVP 功能範圍

### 8.1 P0：可跑真實交易的必要功能

#### 組織與導入

- LINE 登入與店內成員邀請。
- 建立組織、選擇產業與主要模板。
- owner／dispatcher／technician 權限。
- 服務類型、價目表、工作時段、通知模板基本設定。
- 示範資料與導入檢查清單。

#### 接案匣與案件

- 公開報修／詢價表單，可由 LINE 開啟。
- 人工建立電話、LINE 聊天或轉介紹案件。
- 新需求待處理匣、去重提示、指派負責人與下一步。
- 客戶、地點、設備／標的與照片。
- 案件搜尋、篩選、標籤、階段與活動時間軸。

#### 報價

- 從服務價目或模板建立報價。
- 成本與客戶售價分離，權限控制成本可見性。
- 報價草稿、內部核准、不可變版本與客戶分享頁。
- 客戶接受、拒絕、要求聯絡。
- PDF 下載與可撤銷連結。

#### 排程與派工

- 建立工單、日期／時段、預估工時與技師指派。
- 日／週排程與衝突警示。
- 重新排程、改派與原因紀錄。
- 手動發送預約、改期與技師出發通知。

#### 技師現場 PWA

- 今日／即將到來的個人工單。
- 導航、聯絡、出發、到場與施工狀態。
- 產業檢查表、備註與前中後照片。
- 提出異常與追加草稿。
- 完工摘要與客戶確認。
- 弱網路草稿與失敗重試提示。

#### 完工、收款與回訪

- 完工簽認紀錄。
- 應收款、到期日、部分／全部收款與提醒。
- 保固摘要。
- 建立一次性或週期性回訪。
- 到期回訪先進待辦，人工確認後再發送。

#### 通知與稽核

- 已受理、報價、預約、改期、出發、完工、付款與回訪模板。
- 每則通知的草稿、待送、已送達、失敗、取消狀態。
- 組織、案件與工單活動歷程。

### 8.2 P1：Private Beta 後補強

- 語音／LINE 訊息摘要成案件與報價草稿。
- 批次匯入客戶與設備。
- 自訂欄位與檢查表編輯器。
- 報價電子簽名強化與 OTP 驗證。
- 線上付款連結與對帳。
- 多種 LINE OA 串接模式與自動回覆規則。
- 報表匯出、會計系統整合。
- 客戶入口的服務履歷與保固查詢。

### 8.3 明確不做

MVP 不包含：

- 原生 App。
- AI 自動故障診斷或自動承諾報價。
- 全自動客服聊天機器人。
- 完整庫存、採購、發票、會計、薪資。
- 智慧路線最佳化。
- 工程圖、BIM、估驗計價或複雜專案管理。
- 消費者媒合、評價排名或平台抽成。
- 高度客製的企業簽核流程。

## 9. LINE 整合需求

### 9.1 店家端

- 每個 organization 連接自己的 LINE 官方帳號。
- owner 可查看連線狀態、必要權限與最後 webhook 時間。
- channel secret、access token 等敏感資料不得顯示完整值，必須加密保存並可輪替。
- 串接失效時，後台顯示明確影響與修復步驟。

### 9.2 客戶端

- 表單與分享頁需顯示店家名稱、Logo、聯絡方式與隱私說明。
- 客戶可從 LINE 內建瀏覽器完成流程，不強迫跳到外部瀏覽器。
- 所有對客發送都由店家品牌與 OA 發出，Renoly 僅作為技術提供者。
- 連結應有範圍、到期與撤銷機制，避免永久公開 UUID。

### 9.3 可靠性

- webhook 必須驗簽、冪等、可處理重送與順序差異。
- 通知透過 outbox／queue 處理，保留 provider message id、嘗試次數、錯誤與最後狀態。
- 客戶傳入照片需在可取得期限內複製到私有儲存。
- 重複事件不可建立重複案件、重複確認或重複通知。

## 10. 儀表板與指標

MVP 儀表板以可採取行動為優先，不做大量漂亮但無法改善營運的圖表。

主要 KPI：

1. 首次回覆時間：新需求建立至首次有效回覆的中位數。
2. 報價接受率：在期間內有結果的報價中，已接受比例。
3. 完工率：已排定且到期工單中，已完工比例。
4. 回訪轉單率：由回訪建立的新案件中，轉成接受報價／預約的比例。

行動佇列：

- 超過目標時間仍未回覆的新需求。
- 待核准或已送出未回覆的報價。
- 今日未確認、延誤或上傳未完成的工單。
- 已完工但尚未建立／收齊款項的案件。
- 到期但尚未處理的回訪。

指標必須可以點入構成資料，並顯示計算期間與定義。資料不足時顯示「尚無足夠資料」，不可顯示誤導性的 0%。

## 11. 通知策略

所有通知分成三類：

- 交易型：已受理、報價、預約、改期、出發、完工、付款提醒。
- 營運型：店內待辦、衝突、上傳失敗、逾期、串接異常。
- 回訪型：保養、保固檢查、再次服務。

通知規則：

- 報價、追加、取消、完工與付款類通知需明確顯示操作者將送出的內容。
- 回訪預設需人工確認；未來才允許組織選擇自動發送。
- 客戶拒收或封鎖後不得持續發送行銷／回訪訊息。
- 同一事件不得重複發送；重試不得造成客戶收到重複內容。
- 每則通知顯示通道、收件者、內容版本、狀態與時間。

## 12. 資料、安全與隱私要求

- 所有營運資料以 organization 為租戶邊界，資料庫 RLS 與伺服器授權需雙重檢查。
- service role 僅用於受控背景工作，不得作為一般使用者查詢路徑。
- 客戶、地址、電話、照片與服務紀錄屬敏感資料；列表只顯示工作必要資訊。
- 照片使用私有 bucket 與短效 signed URL；驗證真實檔案類型、大小與數量。
- 對外報價、簽認與付款連結使用不可猜測 token，可撤銷、可到期、可記錄使用事件。
- 成本、毛利、內部備註與其他客戶資料不得傳送到公開頁 payload。
- 關鍵變更保留 audit event，不允許一般 UI 永久刪除已送出報價、簽認與收款證據。
- 提供資料匯出、成員停權與組織刪除申請流程。
- 遵循資料最小化原則；公開表單需有個資蒐集告知與同意。

## 13. 非功能需求

### 13.1 裝置與瀏覽器

- 優先支援 360–430 px 寬的手機。
- 支援近期兩個主要版本的 iOS Safari、Android Chrome 與 LINE 內建瀏覽器。
- owner／dispatcher 在平板與桌面可使用雙欄或表格版面。
- 不把 hover 當成唯一操作方式。

### 13.2 效能

- 一般 4G 下，首屏應盡量在 2.5 秒內呈現可理解內容或 skeleton。
- 狀態操作應在 100 ms 內給立即回饋；伺服器確認失敗時回復並說明。
- 照片先顯示本機預覽，再背景壓縮與上傳。
- 長列表採分頁或游標載入，搜尋輸入需 debounce。

### 13.3 可用性與可靠性

- 核心讀取服務月可用性目標 99.5%（Beta 目標）。
- webhook 與通知工作可重試並可人工補送。
- 技師弱網路時可保存文字、檢查表與待上傳照片佇列；恢復連線後明確同步。
- 同一資料被多人更新時，避免靜默覆蓋，提供更新提示或衝突解決。

### 13.4 無障礙與在地化

- 以 WCAG 2.2 AA 為設計目標。
- 觸控目標至少 44 × 44 px，支援鍵盤、可見焦點與螢幕閱讀器名稱。
- 狀態不可只靠顏色，需搭配文字或圖示。
- 日期、時間、電話、地址與金額採台灣格式；時區預設 Asia/Taipei。
- 正式文案使用繁體中文，避免簡體字與不必要英文術語。

## 14. 商業與產品假設

首波方案假設：

- Private Beta 可用低額、可直接驗證續費意願的月費，而非只收口頭承諾。
- 正式方案以每店月費含基本成員數，再針對額外技師或高用量計價。
- 高導入費應對應資料匯入、價目表整理、到店訓練或客製模板，不是為尚未可用的產品預收。

最重要的待驗證假設：

1. 店家願意把大多數合格詢問建立進 Renoly，而不只拿來補紀錄。
2. 技師能在現場持續完成狀態、檢查表與照片，不回到私人 LINE。
3. 老闆願意為少漏單、快報價、可交接與可回訪支付月費。
4. 共通核心能覆蓋首波三個產業，而不用為每店開發專屬流程。
5. 每店導入與每週支援時間可控制在可規模化的範圍。

## 15. MVP 成功條件

產品可進入付費 Beta 的最低門檻：

- 至少 6 家合格店家完成導入，其中至少兩種首波產業。
- 每家至少跑完 10 筆真實案件，不以示範資料計算。
- 至少 70% 的合格真實案件進入系統。
- 至少 80% 已完工工單具有必要狀態與完工紀錄。
- 第 6 家的標準導入時間低於 90 分鐘。
- 第一週後，每店每週人工支援低於 30 分鐘。
- 至少 3／6 支付首月，2／6 願意預付第二個月。
- 至少兩家由回訪、追蹤或漏單提醒帶來可量化結果。

品質門檻：

- owner、dispatcher、technician 的權限測試通過。
- 公開連結不可讀取成本、內部備註或跨組織資料。
- 核心旅程端到端測試通過。
- webhook 重送、通知失敗、照片上傳失敗與弱網路情境有明確恢復方式。
- 無 P0／P1 等級的資料外洩、重複扣款或無法恢復的資料遺失問題。

## 16. 發布階段

### Phase 0：規格與可操作原型

- 完成本文件、前端 IA、API／資料模型與測試策略。
- 使用新資料庫與 seeded demo 建立完整展示流程。
- 以冷氣、水電、抓漏／防水各至少 3 位業者進行流程測試。

### Phase 1：Concierge Pilot

- 3 家設計夥伴跑真實案件。
- 允許團隊在後台協助設定，但記錄每次人工服務時間。
- 每週修正造成漏登、卡關與重複工作的前三大問題。

### Phase 2：Private Beta

- 開放 6–12 家付費測試。
- 鎖定標準模板、導入流程與支援邊界。
- 驗證首月、次月留存、案件滲透率與技師使用率。

### Phase 3：垂直擴張

- 依已驗證需求增加產業模板與合作通路。
- 只有當共通核心穩定，才增加整合、付款與進階自動化。

## 17. 產品決策準則

每個新需求依序回答：

1. 是否改善「接案到收款」的核心流程？
2. 是否至少適用首波三個產業中的兩個？
3. 是否能用模板／設定完成，而非建立分叉產品？
4. 是否讓店家或客戶少一步，而不是增加資料輸入負擔？
5. 是否有可觀察的指標證明價值？
6. 是否增加資料、安全、通知或現場可靠性的風險？

若只服務單一客戶、需要大量客製且無法轉成模板，預設不納入核心產品。

## 18. 待決策事項

下列項目需在開始對外測試前由產品與技術共同定案：

- 每店 LINE OA 串接採全自助或由 Renoly 協助設定。
- 客戶報價接受是否要求手機驗證，及其法務文案。
- dispatcher 送出報價的預設核准政策。
- PWA 離線範圍：僅草稿佇列或完整工單快取。
- 收款 MVP 是否串接單一金流，或先只提供付款資訊與人工對帳。
- 對客公開服務履歷的資料範圍與連結期限。
- 首波定價、基本成員數與照片／訊息用量限制。
