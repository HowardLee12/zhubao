# Renoly v2 使用者旅程與驗收條件

文件狀態：Draft v1  
用途：產品、設計、前端、API 與 E2E 測試的共同驗收依據  
相關文件：[產品規格](./product-spec.md)、[前端規格](./frontend-spec.md)

## 1. 文件使用方式

每條旅程包含：

- 目標：使用者真正想完成的事情。
- 前置條件：開始前系統必須具備的狀態。
- 主要流程：預期的 happy path。
- 例外與恢復：真實使用時必須可處理的狀況。
- 驗收條件：可轉成自動或人工測試的 Given / When / Then。

優先級：

- P0：Private Beta 前必須完整可用並有 E2E 覆蓋。
- P1：可在 Beta 期間補強，不得破壞 P0。

所有驗收以伺服器授權與持久化結果為準；前端隱藏按鈕或顯示成功訊息不能取代後端驗證。

## 2. 共同測試角色與資料

### 2.1 店家與角色

建立兩個彼此完全隔離的測試組織：

- 組織 A「安心工程」：主要模板為到府服務。
- 組織 B「滴水不漏」：主要模板為小型工程。

組織 A 成員：

- 王老闆：owner。
- 林小姐：dispatcher。
- 陳師傅：technician。
- 李師傅：technician，部分案例用於衝突與改派。

組織 B 至少建立 owner 與 technician，用於跨租戶隔離測試。

### 2.2 客戶與案件

- 客戶甲：林太太，單一地址，兩台分離式冷氣。
- 客戶乙：好日子商行，兩個聯絡人與兩個服務地點。
- 客戶丙：陳先生，陽台漏水，需要現勘、多日施工與追加。

測試資料不得使用真實個資。不同組織可建立相同姓名與電話末碼，以驗證去重只發生在租戶內。

### 2.3 共通時區與格式

- 組織時區：Asia/Taipei。
- 金額：新台幣。
- 測試日期使用相對 fixture 或可注入 clock，避免過期測試依賴實際今日。

## 3. 狀態轉移與守門條件

### 3.1 案件階段

案件階段代表商業進度，不由單一工單狀態盲目覆寫。系統可建議下一階段，但關鍵跳轉需確認。

到府服務預設：

待處理 → 待補資料 → 待報價／待現勘 → 待客戶確認 → 待排程 → 已排程 → 進行中 → 待收款 → 已完成

小型工程預設：

新詢問 → 待現勘 → 報價中 → 待客戶確認 → 待開工 → 施工中 → 待驗收 → 待收款 → 保固中／已結案

守門條件：

| 目標階段 | 最低條件 |
|---|---|
| 待客戶確認 | 至少一份已核准且已送出的有效報價，或明確標記免報價 |
| 已排程／待開工 | 至少一張已排程工單 |
| 進行中／施工中 | 至少一張工單已到場或施工中 |
| 待驗收 | 所有必要施工工單完工或有明確未完成例外 |
| 待收款 | 已建立應收，或明確標記本案無需收款 |
| 已完成／已結案 | 必要工單終結、簽認／例外已處理、應收結清或核准結案原因 |

### 3.2 報價

允許轉移：

- 草稿 → 待核准。
- 待核准 → 草稿（退回）或已送出（核准並送出）。
- 已送出 → 已接受、已拒絕、已失效或已撤回。
- 已送出的內容不得回到可編輯草稿；修改時建立新版本。

### 3.3 工單

標準轉移：

未排程 → 已排程 → 已確認 → 已出發 → 已到場 → 施工中 → 待確認 → 已完工

例外：

- 已排程／已確認 → 已取消。
- 已確認／已出發／已到場 → 未到場。
- 已到場／施工中／待確認 → 需再訪。

守門條件：

- 出發前需有被指派 technician、日期、服務地點。
- 完工前需完成模板要求的檢查項目、必要照片與完工摘要。
- 缺少必要項目時只有 owner 可填理由後例外完工，且產生 audit event。
- 已完工或取消後的回退需 owner、理由與事件紀錄。

### 3.4 追加／追減

草稿 → 待內部核准 → 待客戶確認 → 已接受／已拒絕／已撤回

technician 只能建立草稿；未被客戶接受的金額不得納入已確認總額、付款要求或毛利報表。

## 5. J01 — owner 建立店家並邀請團隊

目標：owner 從首次 LINE 登入開始，在不需技術人員協助的情況下建立可接第一筆案件的工作空間。

前置條件：

- 使用者尚未加入任何 organization。
- LINE 登入服務可用。

主要流程：

1. 王老闆使用 LINE 登入。
2. 建立「安心工程」，填寫店家聯絡資料與工作時間。
3. 選擇冷氣模板；系統預覽預設服務、欄位、檢查表與回訪週期。
4. owner 接受模板並調整兩個服務價格。
5. owner 邀請林小姐為 dispatcher、陳師傅為 technician。
6. owner 可先略過 LINE OA 串接，改用公開表單連結／手動分享。
7. 完成頁顯示尚未串接 LINE 的影響與「建立第一筆案件」。
8. 受邀成員登入後進入與角色相符的首頁。

例外與恢復：

- LINE 登入取消：不建立半套使用者／組織。
- 組織名稱重複：允許不同租戶同名，不以全域唯一阻擋。
- 邀請連結過期：owner 可撤銷並重送；舊連結持續無效。
- 模板／價目儲存失敗：保留畫面輸入並可重試。
- 最後一位 owner 不可自行降級或移除。

驗收條件：

- J01-AC01：Given 新使用者完成 LINE 登入，When 建立組織，Then 該使用者成為唯一初始 owner，organization 與 membership 一次成功或全部失敗。
- J01-AC02：Given owner 選冷氣模板，When 完成模板步驟，Then 新案件預設使用到府服務階段、冷氣欄位、必要照片與 6／12 個月回訪選項。
- J01-AC03：Given owner 在導入中關閉頁面，When 再次登入，Then 回到上次未完成步驟且已保存欄位仍在。
- J01-AC04：Given dispatcher 接受有效邀請，When 登入，Then 可進工作台與接案匣，但無法查看方案、secret 或變更 owner 角色。
- J01-AC05：Given technician 接受邀請，When 登入，Then 首頁為「今日」，且無法透過 UI 或直接請求取得全店客戶與成本資料。
- J01-AC06：Given owner 略過 LINE 串接，When 完成導入，Then 仍可建立案件與分享公開表單，頁面清楚標記自動通知尚不可用。
- J01-AC07：Given 邀請已撤銷或過期，When 任何人開啟，Then 不加入組織、不洩漏成員名單，並顯示向 owner 索取新邀請。

## 6. J02 — 客戶從 LINE 提交需求

目標：客戶不下載 App，即可用店家品牌表單提交足夠的詢價／報修資料並得到明確回覆預期。

前置條件：

- 組織已啟用公開需求表單。
- 至少一個服務類型啟用。

主要流程：

1. 林太太從店家 LINE 圖文選單開啟需求表單。
2. 頁首顯示「安心工程」品牌、聯絡方式與個資說明。
3. 客戶選「冷氣清洗」，填寫兩台分離式冷氣、問題描述。
4. 上傳室內機全景、銘牌與現況照片。
5. 填寫聯絡人、電話、地址與兩個可到場時段。
6. 預覽提交內容並同意個資蒐集告知。
7. 送出後看到參考碼、預計回覆時間與聯絡店家按鈕。
8. 系統只建立一筆 intake，接案匣 badge 增加。

例外與恢復：

- 客戶在送出前關閉：同裝置於保存期限內可恢復草稿。
- 照片過大／格式不符：逐張提示，不清空其他內容。
- 部分照片上傳失敗：成功項目保留，可重試失敗項目。
- 送出逾時：前端先查詢 idempotency 結果，再決定重試。
- 店家暫停接單：表單開始前即告知，顯示其他聯絡方式。
- 客戶重複點送出：回到同一成功結果，不建立重複 intake。

驗收條件：

- J02-AC01：Given 客戶從 LINE 內建瀏覽器開啟有效表單，When 完成必填資料並送出，Then 不要求安裝 App 或建立 Renoly 帳號。
- J02-AC02：Given 尚未同意個資告知，When 點送出，Then 系統阻擋並將焦點移到同意欄位，既有資料不遺失。
- J02-AC03：Given 一張照片格式不支援，When 選擇檔案，Then 只拒絕該檔、說明支援格式，其他照片與表單資料保留。
- J02-AC04：Given 同一 submit key 被送出兩次，When 後端處理，Then 僅有一筆 intake 與一組照片關聯，兩次回應指向同一結果。
- J02-AC05：Given intake 建立成功，When dispatcher 查看接案匣，Then 可看到來源、收到時間、服務類型、客戶、區域、照片數與未回覆計時。
- J02-AC06：Given 店家暫停公開接單，When 客戶開啟表單，Then 不顯示可送出的表單，且不在填完後才告知。
- J02-AC07：Given 組織 B 猜測組織 A 的參考碼，When 嘗試查詢，Then 無法取得 intake 或客戶資料。

## 7. J03 — dispatcher 分流進件並建立案件

目標：dispatcher 快速判斷需求、補足資料、避免重複，並把合格需求交給明確負責人與下一步。

前置條件：

- J02 已產生一筆待處理 intake。
- dispatcher 屬於同一 organization。

主要流程：

1. 林小姐在接案匣看到最久未回覆需求。
2. 開啟後比對原始內容與系統整理摘要。
3. 系統提示相似電話／地址，dispatcher 確認是既有客戶林太太，但不是重複案件。
4. 連結既有客戶，新增第二個地址或設備資料（需要時）。
5. 設定優先度、服務類型、責任人與下一步。
6. 資料不足時從模板產生補資料訊息並預覽後送出。
7. 資料完成後建立案件；intake 顯示已轉換且不可再次轉換。

例外與恢復：

- 系統摘要錯誤：dispatcher 依原始內容修改，保留兩者與修正事件。
- 真正重複：選擇主 intake 後合併照片／事件，不刪除來源證據。
- 垃圾／非服務範圍：填原因後封存，不污染案件轉換率。
- 兩位 dispatcher 同時領取：採版本控制，第二位看到最新責任人。
- LINE 補資料訊息失敗：案件仍保留待補狀態，可重試或複製連結。

驗收條件：

- J03-AC01：Given intake 尚未指派，When dispatcher 領取，Then 責任人與時間被記錄，其他使用者即時或下次更新時看到結果。
- J03-AC02：Given 系統找到相似客戶，When dispatcher 建立案件，Then 必須人工選擇連結既有或建立新客戶，不可自動合併。
- J03-AC03：Given intake 缺少必要照片，When dispatcher 送出補資料要求，Then 案件為待補資料、通知有預覽與事件紀錄，客戶只看到需要補的欄位。
- J03-AC04：Given 同一 intake 已轉成案件，When 再次呼叫轉換，Then 回傳既有案件而非建立第二筆。
- J03-AC05：Given dispatcher 更正整理摘要，When 儲存，Then 原始客戶輸入保持不可變，摘要記錄最後編輯者與時間。
- J03-AC06：Given 通知傳送失敗，When 回到詳情，Then 看得到失敗原因、重試與複製連結；案件資料不回退或遺失。
- J03-AC07：Given intake 被封存為不適用，When 檢視報價轉換 KPI，Then 不被計入合格案件分母，仍可由 owner 稽核。

## 8. J04 — 建立、核准、送出與確認報價

目標：店家快速產生準確報價，保護成本資料，經人工核准後讓客戶在 LINE 安全確認。

前置條件：

- 已有案件、客戶與服務範圍。
- owner 已設定服務價目；或允許手動項目。

主要流程：

1. dispatcher 從案件建立報價草稿。
2. 從冷氣價目加入「分離式冷氣清洗 × 2」與加購項目。
3. 填寫效期、施工範圍、排除項目、付款條件。
4. 預覽客戶版並送交 owner 核准。
5. owner 查看成本、毛利與客戶版差異，核准並選擇 LINE 模板。
6. 系統建立不可變版本、發送安全連結並將狀態設為已送出。
7. 客戶開啟頁面，只看到客戶內容，選擇接受。
8. 系統記錄決定、時間、版本與來源；案件進入待排程。

例外與恢復：

- owner 退回：保留草稿並列出原因。
- 已送出後發現錯誤：撤回舊版、複製成新版；舊版不可原地改。
- 客戶開啟舊版：顯示已更新並導向最新有效版。
- 報價過期：不可接受，可要求店家聯絡。
- 客戶拒絕：可選原因或要求聯絡，不自動刪除案件。
- 通知失敗：報價版本仍存在且狀態清楚，可補送。

驗收條件：

- J04-AC01：Given dispatcher 沒有直接送出權限，When 完成草稿，Then 只能送核，無法透過 API 將狀態改為已送出。
- J04-AC02：Given owner 核准並送出，When transaction 完成，Then 報價版本、項目快照、公開 token、通知 outbox 與 audit event 一致建立；部分失敗不可留下假成功。
- J04-AC03：Given 客戶取得公開報價 DTO，When 檢查 network response 與 HTML，Then 不包含成本、毛利、內部備註或其他客戶資料。
- J04-AC04：Given 已送出 v1，When 店家修改內容，Then 系統建立 v2，v1 的項目、總額與事件保持不變。
- J04-AC05：Given 客戶已接受 v1，When 相同 token 重複提交接受，Then 回傳既有決定且只產生一次商業事件。
- J04-AC06：Given 報價已過效期或被撤回，When 客戶提交接受，Then 後端拒絕，畫面顯示聯絡店家且不改案件階段。
- J04-AC07：Given 客戶接受有效報價，When 回到案件，Then 顯示接受版本、時間、確認總額與「建立工單」下一步。
- J04-AC08：Given 客戶選拒絕，When 提交，Then 報價為已拒絕，案件回到需店內跟進而非自動結案。

## 9. J05 — 建立工單、派工與預約確認

目標：dispatcher 把已接受案件安排給正確技師，避免衝突，並讓客戶與技師得到一致資訊。

前置條件：

- 報價已接受或案件標記免報價。
- 客戶、地址、聯絡與服務內容完整。

主要流程：

1. dispatcher 從案件建立工單。
2. 選擇日期、時間窗、預估工時、陳師傅與冷氣檢查表。
3. 系統檢查陳師傅工作時間與其他工單，無衝突。
4. dispatcher 預覽客戶預約通知與技師任務摘要。
5. 儲存後工單為已排程，客戶收到確認連結，技師在任務列表看到。
6. 客戶確認時段，工單轉為已確認。
7. 所有人看到相同時段與最後更新時間。

例外與恢復：

- 技師時間重疊：顯示衝突原因與現有工單；owner 可填原因覆寫。
- 客戶要求改期：進入待處理改期，不直接選一個可能衝突的時段。
- 通知失敗：排程仍保存，顯示需補送。
- 未指派技師：可存成未排程草稿，但不可發送「已預約」。
- 多日工程：建立多張有明確目的的工單，而非一張無限期工單。

驗收條件：

- J05-AC01：Given 工單缺少地址、日期或技師，When dispatcher 嘗試發送預約，Then 系統阻擋並指出缺少欄位。
- J05-AC02：Given 陳師傅同時已有工單，When 安排重疊時段，Then UI 與 API 都回報衝突；一般 dispatcher 不得無理由覆寫。
- J05-AC03：Given 工單成功排程，When technician 重新整理任務，Then 看到客戶必要稱呼、地址、時段、服務內容與現場注意事項，但看不到成本／毛利。
- J05-AC04：Given 客戶確認有效預約，When 重複點確認，Then 工單只有一個確認事件且保持已確認。
- J05-AC05：Given 客戶提出改期，When dispatcher 開啟排程，Then 原時段仍保留並標記待處理，直到新時段被明確確認。
- J05-AC06：Given LINE 通知失敗，When 工單已儲存，Then 不回退到未排程；通知中心提供重試，技師端仍可見任務。

## 10. J06 — technician 執行到府服務並上傳前後照

目標：technician 以最少操作完成出發、到場、檢查、施工與證據紀錄，dispatcher 不需從私人 LINE 補資料。

前置條件：

- 工單已指派給陳師傅並已確認。
- 技師裝置已登入且下載今日任務。

主要流程：

1. 陳師傅在「今日」看到下一張工單。
2. 點出發；系統記錄時間並建立已核准的客戶出發通知。
3. 透過導航到地址，點到場，再開始施工。
4. 依冷氣模板填設備、檢查項目，拍每台設備施工前照片。
5. 完成清洗後拍施工後照片，填結果與客戶可見建議。
6. 系統檢查必要照片與欄位均完成。
7. 技師送到待確認；客戶現場或遠端簽認後完工。
8. dispatcher 在案件看到狀態、時間與分類照片，不需另行索取。

例外與恢復：

- 客戶不在場：可改用遠端完工連結。
- 發現設備與報修資料不同：更新設備草稿並標記待 dispatcher 確認。
- 發現額外問題：建立異常／追加草稿，不直接改價。
- 照片未同步：工單可到待確認，但除 owner 例外外不可最終完工。
- 誤觸狀態：短時間可撤銷低風險狀態；已通知客戶後需理由。

驗收條件：

- J06-AC01：Given technician 未被指派，When 嘗試存取工單 URL 或 API，Then 回傳無權限且不洩漏客戶、地址、照片。
- J06-AC02：Given 工單為已確認，When technician 點出發，Then 立即顯示狀態與同步結果，server 記錄操作者與時間。
- J06-AC03：Given 冷氣模板要求每台一張前照與後照，When 兩台設備只有一張後照，Then 完工被阻擋並指出缺少哪台設備的照片。
- J06-AC04：Given 照片先顯示本機預覽，When 上傳成功，Then 縮圖、分類、工單、設備、上傳者與時間正確關聯。
- J06-AC05：Given technician 填寫內部備註，When 客戶開啟完工頁，Then 只顯示客戶可見摘要，不包含內部備註。
- J06-AC06：Given technician 建立追加草稿，When 儲存，Then 客戶不會收到通知，案件確認總額不變，owner／dispatcher 收到待處理項目。
- J06-AC07：Given 必要紀錄完成，When technician 送到待確認，Then 工單保留完整時間軸，案件顯示下一步為客戶／內部確認。

## 11. J07 — 多日小型工程與追加簽認

目標：抓漏／防水團隊能管理現勘、多日工單與現場追加，避免口頭追加無法請款。

前置條件：

- 小型工程案件已接受報價。
- 已建立現勘、施工、試水／驗收工單。

主要流程：

1. technician 執行第一天施工並依區域上傳前／中照片。
2. 發現拆除後基底損壞，建立追加草稿，附照片、原因、建議處理與工期影響。
3. owner 補上項目與金額，核准並預覽客戶版。
4. 客戶開啟追加頁，看到原範圍、變更、新總額與延長天數。
5. 客戶接受；系統記錄版本並更新已確認總額。
6. dispatcher 新增／調整後續工單，但保留原排程歷程。
7. 後續完工與應收引用已接受的原報價＋追加。

例外與恢復：

- 客戶拒絕追加：原報價範圍保持不變，產生待店內決策。
- 緊急安全處理：可先建立零元／待定草稿與現場證據，不可假設客戶接受金額。
- 已接受後再變更：建立新 change order，不修改舊紀錄。
- 追加通知失敗：狀態與通知分離，允許補送。

驗收條件：

- J07-AC01：Given technician 建立追加，When 儲存，Then 狀態只可為草稿，不能直接進入待客戶確認或修改確認總額。
- J07-AC02：Given owner 核准 NT$8,000 追加，When 客戶開啟頁面，Then 顯示原確認總額、增加金額、新總額、工期影響與證據；不顯示成本。
- J07-AC03：Given 客戶接受追加，When 交易完成，Then change order、確認事件、案件總額與後續應收計算一致更新。
- J07-AC04：Given 客戶拒絕追加，When dispatcher 查看案件，Then 原確認總額不變，追加標記已拒絕並出現「確認原範圍／重新提案」待辦。
- J07-AC05：Given 已接受追加，When owner 想修改金額，Then 系統要求建立新版／新追加，舊版保持不可變。
- J07-AC06：Given 追加連結被重複提交，When 後端收到相同或衝突決定，Then 同決定冪等；不同決定在已完成後被拒絕並顯示既有結果。

## 12. J08 — 完工摘要與客戶簽認

目標：店家以一致的完工摘要、照片與未完成事項取得可稽核客戶確認，不把「按完工」當成缺乏內容的終態。

前置條件：

- 所有必要施工工單已到待確認。
- 必要照片、檢查表與客戶可見摘要完成。

主要流程：

1. technician 或 dispatcher 檢查完工摘要。
2. 系統列出完成項目、前後照片、排除／待處理項目、保固。
3. 由現場 QR／同裝置或 LINE 安全連結交給客戶。
4. 客戶選擇「確認完成」並送出。
5. 系統記錄簽認版本、時間、來源與當時內容快照。
6. 工單轉已完工；案件依收款狀態進入待收款或已完成。

例外與恢復：

- 客戶選「有問題需處理」：建立 issue，工單保持待確認或轉需再訪。
- 客戶不在場：發遠端連結，不假設已簽認。
- 客戶拒絕提供簽認：owner 可填理由做例外完工，紀錄與客戶簽認明確區分。
- 送出時斷線：先查詢結果，避免重複。

驗收條件：

- J08-AC01：Given 缺少模板必要照片，When 發送完工簽認，Then 系統阻擋並列出缺項。
- J08-AC02：Given 客戶確認完成，When 後端接受，Then 保存不可變內容快照、客戶決定、時間、來源與關聯工單。
- J08-AC03：Given 客戶回報問題，When 提交，Then 不把工單標為已完工；建立 owner／dispatcher 可見 issue 並保留客戶描述。
- J08-AC04：Given owner 使用例外完工，When 儲存，Then 必須有理由與 audit event，UI 不可顯示成「客戶已簽認」。
- J08-AC05：Given 簽認完成後店家修改客戶可見摘要，When 查看歷程，Then 原簽認快照不變；新內容需重新簽認才可取代。
- J08-AC06：Given 客戶連結已完成，When 再次開啟，Then 顯示既有結果與下一步，不重複送出。

## 13. J09 — 建立應收、提醒與記錄付款

目標：店家知道每案應收、已收、餘額與到期狀態，並能安全處理部分付款與重複回呼。

前置條件：

- 有已接受報價／追加，或 owner 有權建立手動應收。

主要流程：

1. owner／dispatcher 從確認金額建立訂金、階段款或尾款。
2. 填到期日、金額與付款方式，預覽後傳給客戶。
3. 客戶頁顯示應付、已付、餘額、用途與店家資訊。
4. 店家收到轉帳後記錄部分或全部付款；若串金流則由驗證回呼記錄。
5. 系統更新付款與案件餘額，保留每次 payment record。
6. 餘額歸零且其他守門完成後，案件可完成／結案。

例外與恢復：

- 實收大於餘額：阻擋或進入待對帳，不能靜默變負數。
- 同一金流回呼重送：只記錄一次。
- 人工標記與回呼衝突：待對帳，不重複累計。
- 付款通知失敗：應收仍存在，可補送。
- 作廢：保留原紀錄與原因，不永久刪除。

驗收條件：

- J09-AC01：Given 已確認總額 NT$20,000，When 建立 NT$5,000 訂金與 NT$15,000 尾款，Then 應收總額、已收與餘額計算一致。
- J09-AC02：Given 客戶先付 NT$3,000，When 記錄部分付款，Then 狀態為部分付款、餘額正確且保留付款方式與時間。
- J09-AC03：Given 同一 provider transaction id 回呼兩次，When 處理，Then 只產生一筆付款紀錄與一次餘額變更。
- J09-AC04：Given 客戶開啟付款頁，When 檢查 payload，Then 不包含成本、毛利、其他應收或其他客戶資料。
- J09-AC05：Given 應收逾期，When 日期跨過到期日，Then 顯示已逾期與天數，但不自動重複發送提醒。
- J09-AC06：Given owner 作廢應收，When 儲存，Then 要求理由、保留 audit event，客戶舊連結顯示已作廢。
- J09-AC07：Given 所有餘額已結清，When 案件仍有未完成工單，Then 不得只因付款完成自動結案。

## 14. J10 — 建立保固／回訪並轉成新案件

目標：完工資料能在正確時間變成可行動回訪，並衡量是否帶來新案件，而不是成為無人看的設備履歷。

前置條件：

- 案件已完工。
- 客戶有可使用的聯絡通道且未拒收回訪。

主要流程：

1. dispatcher 在完工時選擇保固起訖與 6／12 個月保養。
2. 系統在到期前建立 follow-up 待辦，不直接發送。
3. dispatcher 查看來源設備、上次服務與客戶偏好，預覽 LINE 訊息。
4. 送出後記錄通知。
5. 客戶選有興趣或要求聯絡。
6. dispatcher 一鍵建立新案件，帶入客戶、地址、設備、上次服務與 follow-up source。
7. 新案件接受報價後，回訪標記已轉單並計入回訪轉單率。

例外與恢復：

- 客戶拒收：禁止發送，標記原因。
- LINE 封鎖／失敗：提供合規的其他通道或人工聯絡，不持續自動重試。
- 同設備已有進行中案件：提示連結或合併，避免重複回訪。
- 到期規則改變：既有排程是否更新需 owner 明確選擇。

驗收條件：

- J10-AC01：Given 建立 6 個月回訪，When 保存，Then 使用組織時區計算明確日期並顯示於客戶／設備與回訪列表。
- J10-AC02：Given 回訪到期，When scheduler 執行，Then 只建立一筆待辦，不在預設政策下自動傳給客戶。
- J10-AC03：Given 客戶已標記拒收，When dispatcher 嘗試發送，Then UI 與 API 均阻擋並顯示允許的聯絡方式。
- J10-AC04：Given 客戶由回訪建立新案件，When 新案件生成，Then 保留 source follow-up、原案件與設備關聯，不複製不必要舊照片。
- J10-AC05：Given 回訪新案件的報價已接受，When 計算 KPI，Then 該 follow-up 計為轉單一次；重複事件不重複計數。
- J10-AC06：Given 同設備已有進行中案件，When 建立回訪案件，Then 系統先提示既有案件並要求人工選擇。

## 15. J11 — 改期、改派、取消與未到場

目標：排程例外不靠私訊處理；客戶、dispatcher 與 technician 看到一致結果與歷程。

### 情境 A：客戶要求改期

1. 客戶從預約頁提出兩個可行時段。
2. 原工單保持原時段並標記「改期處理中」。
3. dispatcher 選新時段並檢查技師衝突。
4. 預覽通知後保存，客戶與技師收到更新。
5. 原時段與變更原因保留於歷程。

### 情境 B：dispatcher 改派

1. 陳師傅臨時請假。
2. dispatcher 在排程選擇李師傅。
3. 系統檢查權限、技能／可用性與衝突。
4. 改派成功後，陳師傅失去客戶資料存取，李師傅取得任務。

### 情境 C：取消／未到場

1. dispatcher 取消需選擇店家／客戶原因並處理通知。
2. technician 到場但無法聯絡客戶，可標記未到場並附聯絡嘗試。
3. 系統建立後續待辦：重新排程、收取空趟費（若適用）或結束。

驗收條件：

- J11-AC01：Given 客戶只提交改期需求，When dispatcher 尚未確認，Then 原工單不直接移動，所有人看到「改期處理中」。
- J11-AC02：Given 新時段確認，When 保存成功，Then 工單只有一個目前時段，歷程保留舊時段、原因、操作者與通知。
- J11-AC03：Given 工單由陳師傅改派李師傅，When 改派完成，Then 陳師傅無法再讀客戶敏感資料，未同步的合法現場紀錄仍不遺失。
- J11-AC04：Given 已出發工單要取消，When dispatcher 操作，Then 必須填理由並明確決定是否通知技師與客戶。
- J11-AC05：Given technician 標記未到場，When 儲存，Then 要求至少一筆聯絡嘗試／說明，工單進入例外終態並建立後續待辦。
- J11-AC06：Given 改期通知失敗，When 排程已保存，Then 顯示明確風險與補送動作，不把已改時段靜默回退。

## 16. J12 — 技師弱網路與照片同步恢復

目標：地下室、機房或訊號不佳現場仍可留下可靠資料，並清楚區分本機已存與伺服器已同步。

前置條件：

- technician 已在線時下載被指派工單。
- 裝置支援本機草稿儲存。

主要流程：

1. 技師開啟已快取工單後失去網路。
2. 畫面顯示離線、最後同步與待同步數。
3. 技師填檢查表、備註並拍三張照片。
4. 每項資料取得本機 id，顯示「等待同步」。
5. 網路恢復後，佇列依安全順序上傳；重試不建立重複照片。
6. 同步完成後狀態改為已同步，dispatcher 可見。
7. 若伺服器資料已變更，進入衝突處理而非靜默覆蓋。

例外與恢復：

- App 被系統關閉：重新開啟仍看得到待同步項目。
- 單張照片失敗：其他項目繼續，失敗項目可個別重試。
- 權限在離線期間被移除：恢復連線後停止上傳敏感資料並引導聯絡 owner；已拍資料依安全政策處理。
- 裝置空間不足：拍攝前／保存時說明，避免顯示假成功。
- 登出：有待同步資料時阻擋並說明。

驗收條件：

- J12-AC01：Given 工單已快取且網路中斷，When 技師填表與拍照，Then 畫面不宣稱已同步，資料在重新載入後仍存在。
- J12-AC02：Given 三張照片等待同步，When 第二張上傳失敗，Then 第一、三張可完成，第二張保留錯誤與重試，不複製成功照片。
- J12-AC03：Given 同一 local id 重試多次，When 後端接收，Then 只建立一筆 photo resource。
- J12-AC04：Given 有待同步資料，When 技師登出，Then 系統阻擋並提供先同步或明確放棄本機資料的受控流程。
- J12-AC05：Given dispatcher 在線修改檢查表模板，When 技師同步舊版答案，Then 系統保留答案版本並提示新增必要欄位，不靜默丟棄。
- J12-AC06：Given technician 在離線期間被停權，When 恢復連線，Then session 失效、不可讀取新資料，待同步敏感內容不傳至錯誤組織或帳號。

## 17. J13 — 權限、跨租戶與成員停權

目標：角色只看到工作需要資料，任何 URL 猜測、前端竄改或組織切換都不能突破租戶邊界。

### 情境 A：角色權限

- owner 可管理組織、團隊、價格、核准與方案。
- dispatcher 可處理案件／排程，但預設不能管理 secret、方案或 owner。
- technician 只看被指派工單的必要內容。

### 情境 B：跨租戶

- 組織 A 與 B 資料即使 UUID、電話或名稱相似，也不可互讀／互改。
- service role 只存在受控背景工作，不接受前端傳入 organization 作為唯一授權依據。

### 情境 C：停權／改派

- owner 停權成員後，現有 session 在合理時間內失效。
- 已建立的事件保留原操作者，不因停權被刪除。

驗收條件：

- J13-AC01：Given technician 知道未指派工單 id，When 直接請求頁面、API、signed photo URL，Then 均被拒絕且不透露資源內容。
- J13-AC02：Given dispatcher 修改 request payload 嘗試將自己升為 owner，When 送出，Then 後端拒絕並記錄安全事件。
- J13-AC03：Given 組織 A owner 使用組織 B 資源 id，When 查詢／更新／刪除，Then 回傳安全的不存在或無權限結果，資料不變。
- J13-AC04：Given owner 停權 technician，When 該 technician 再次 mutation 或刷新資料，Then session／membership 驗證失敗，已同步 audit event 仍顯示原姓名或歷史識別。
- J13-AC05：Given owner 切換組織，When 新組織載入，Then 前一組織的 query cache、照片 URL、搜尋結果與 notification badge 不出現在畫面。
- J13-AC06：Given 組織只剩一位 owner，When 嘗試降級、停權或離開，Then UI 與 API 都阻擋並說明需先指定另一位 owner。
- J13-AC07：Given 公開客戶 token 有效，When 使用 token 呼叫內部 API，Then 不取得任何店內權限。

## 18. J14 — 客戶安全連結過期、撤銷與重入

目標：客戶能安全重開有效連結、查看既有結果；失效連結不造成資料外洩或重複商業動作。

前置條件：

- 至少建立報價、預約、追加、簽認或付款公開 token。

主要流程：

1. 客戶從 LINE 開啟有效連結。
2. 系統只載入 token scope 允許的資源與動作。
3. 客戶完成決定後重開連結，看到既有結果。
4. 到期或被撤銷後，頁面顯示無法繼續與聯絡店家。

例外與恢復：

- token 出現在其他裝置：依風險政策要求手機末碼／LINE 綁定。
- 新版本取代舊版本：舊 token 不可確認舊價格。
- URL 被搜尋引擎或預覽 bot 開啟：不因 GET 產生接受／已讀完等商業決定。
- 客戶提交時 token 剛過期：後端以接收時間與政策裁決，結果明確。

驗收條件：

- J14-AC01：Given 有效 token 僅允許查看 quote v2，When 請求其他 quote／case／photo id，Then 不可越權擴大 scope。
- J14-AC02：Given token 已撤銷或不存在，When 開啟，Then 使用一致安全錯誤頁，不顯示客戶名、案件是否存在或撤銷原因細節。
- J14-AC03：Given 客戶已接受報價，When 再次開啟，Then 顯示接受結果、版本與下一步，不再顯示可重複接受按鈕。
- J14-AC04：Given link preview bot 發出 GET，When 頁面載入，Then 不建立客戶決定、不變更報價狀態。
- J14-AC05：Given 新版本取代舊版，When 客戶使用舊 token 提交接受，Then 後端拒絕並導向最新有效版本。
- J14-AC06：Given 公開頁載入，When 檢查快取 header 與 URL，Then 敏感頁不被共享快取，URL 不含客戶姓名、電話或地址。

## 19. J15 — 搜尋、交接與稽核追溯

目標：任何有權限的人都能快速找到案件並理解下一步；owner 能追查關鍵商業決定。

前置條件：

- 組織內有多位客戶、案件、報價與工單。

主要流程：

1. dispatcher 以電話末碼或地址搜尋客戶／案件。
2. 從搜尋結果進入案件總覽。
3. 在 30 秒內看到目前階段、責任人、下一步、有效報價、下一張工單與應收。
4. dispatcher 將責任人交接給另一位成員並填說明。
5. owner 在歷程查到報價核准、客戶接受、改期、追加、完工與付款事件。

驗收條件：

- J15-AC01：Given 搜尋電話末碼，When 有多筆符合，Then 結果以客戶、區域與最近案件協助辨識，不顯示超過角色權限的資料。
- J15-AC02：Given 使用者套用篩選並開啟案件後返回，When 列表恢復，Then 搜尋、篩選與捲動位置保留。
- J15-AC03：Given 責任人交接，When 保存，Then 新責任人、時間、說明與舊責任人記錄於歷程，相關待辦轉移。
- J15-AC04：Given owner 查看 audit timeline，When 展開報價接受事件，Then 可識別版本、時間、來源與內容快照，不能由一般 UI 刪除。
- J15-AC05：Given KPI 點入構成資料，When 查看清單，Then 筆數與指標公式一致，排除條件可見。

## 20. 跨旅程驗收

### 20.1 客戶免安裝 App

- 所有 customer P0 旅程可在 LINE 內建瀏覽器完成。
- 不要求下載、建立密碼或加入 Renoly 後台。
- 客戶退出後可從同一有效連結回到當前結果。

### 20.2 人工確認

- AI／規則可建立摘要、建議與草稿。
- 報價送出、追加送出、取消、例外完工、付款作廢與回訪發送都有可識別的人員確認。
- 自動化失敗不會讓草稿看似已經對客生效。

### 20.3 稽核一致性

以下事件必須記錄 organization、actor／system、timestamp、resource、action 與必要的 before／after 或 version：

- 角色與成員變更。
- 報價核准、送出、撤回與客戶決定。
- 工單改期、改派、取消、例外完工。
- 追加核准與客戶決定。
- 完工簽認。
- 付款建立、記錄、作廢與對帳。
- 公開連結撤銷。

### 20.4 通知與資料狀態分離

- 通知失敗不回退已正確保存的報價、排程或付款資料。
- 資料保存失敗時不得先建立看似成功的通知。
- 重試通知沿用同一業務通知識別，不因 provider 重試建立重複商業事件。

### 20.5 模板共通性

至少以下兩條 E2E 使用相同核心案件／工單／報價 API 與 UI 元件：

- 冷氣：進件 → 報價 → 單次工單 → 前後照 → 完工 → 6 個月回訪。
- 抓漏防水：進件 → 現勘 → 報價 → 多工單 → 追加 → 驗收 → 階段／尾款 → 保固。

差異只能來自模板欄位、檢查表、必要照片、預設階段與顯示模組；不得為每個產業複製整套頁面與資料模型。

## 21. MVP E2E 最小集合

發布前至少自動化以下情境：

1. owner 建立組織、選模板並邀請 dispatcher／technician。
2. 客戶免登入提交冷氣需求與照片，重複送出不重複建案。
3. dispatcher 轉進件為案件、建立報價並送核。
4. owner 核准送出，客戶接受；公開 payload 無成本。
5. dispatcher 排程且處理衝突，technician 只能看到自己的工單。
6. technician 出發、到場、前後照、檢查表、待確認；缺項無法完工。
7. 客戶簽認、建立應收、部分付款與結清。
8. 抓漏案件建立追加，客戶接受後才更新總額。
9. 客戶改期、dispatcher 確認新時段、舊時段保留歷程。
10. 技師離線草稿與照片重連同步，不重複建立資料。
11. 組織 A 無法讀寫組織 B 的案件、照片與公開連結資料。
12. 報價過期／撤回、通知失敗、照片失敗均有可恢復結果。

## 22. Pilot 人工驗收腳本

每家試點使用真實但經客戶同意的案件，依序觀察：

1. 店家能否在 90 分鐘內完成基本設定、價目與首位技師邀請。
2. 客戶是否能在無協助下送出一筆需求。
3. dispatcher 是否能在 5 分鐘內從進件建立可核准報價。
4. owner 是否理解內部成本與客戶版內容的邊界。
5. technician 是否在現場不需回到私人 LINE 傳照片。
6. 完工後是否能從紀錄直接建立簽認、應收與回訪。
7. 一週後合格案件進系統比例是否達 70%。
8. 已完工工單必要紀錄完整率是否達 80%。
9. 第一週後每店每週人工支援是否低於 30 分鐘。

任何需要 Renoly 團隊代打資料、手動修 DB、私訊補通知或口頭解釋狀態的情況，都要記為產品／導入成本，不得算作「使用者成功完成」。

## 23. 發布阻擋條件

出現以下任一情況不得發布付費 Beta：

- 跨 organization 可讀取或修改資料。
- technician 可取得未指派客戶資料、成本或毛利。
- 公開客戶頁 payload 含內部欄位。
- 報價／追加／付款的重複提交造成重複金額或事件。
- 照片顯示已完成但實際未保存且無恢復方式。
- 已送出報價可被原地修改，或簽認內容沒有版本快照。
- 客戶拒絕／過期／撤回後仍能透過舊連結完成決定。
- 通知失敗會遺失已保存的案件、排程或報價。
- 核心手機流程只能靠 hover、精細拖曳或小於 44 px 的唯一操作完成。
- owner、dispatcher、technician 任一 P0 主旅程沒有可重現的測試結果。
